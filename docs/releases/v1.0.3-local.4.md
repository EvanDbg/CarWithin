# CarWithin Local v1.0.3-local.4

应用版本：**1.0.3 / build 19**。实验性预发布，用于核对 StartSession 的配对标识。尚未在实体 iPhone 上验证本次改动能够建立 CarPlay 控制连接或出现画面。

## 已确认的现象

build 18 的真机反馈中，直接回环和 LocalDevVPN 均已完成 MFi 配件认证和识别。两轮测试分别从 21:47:52 到 21:48:37、21:49:06 到 21:49:51，完整等待 45 秒后停止，期间没有“控制入站”。VPN 模式的 App 回送探测成功。故障仍在 StartSession 发送后、App 接受控制 TCP 之前；这些日志不能证明 iOS 是否发出了 SYN 或具体在哪个系统条件上被阻断。

## 本次变化与依据

- field 4 从 build 18 的 Ed25519 公钥 hex 改成活动接收器的 `AirPlayCredentials.identifier`，以 UTF-8 字符串及 NUL 结束符编码。这个持久标识与 PairSetup/PairVerify 使用的身份一致，本 App 中通常为 36 字节 UUID；不另外生成标识，不重建密钥。
- 监听器在自己的队列上取得实际端口及标识快照，再通过已有启动 token 检查传给主线程。iAP2 建链之前检查请求，重试复用同一份编码。
- 本机模式拒绝缺失、空白/控制字符或过长的标识。原远端 iPad 请求继续保留未知身份的空字段，不使用发送手机的身份代替。
- 每次启动记录系统版本和 App build；等待提示说明无控制连接时约 45 秒停止。日志说明本次 field 4 使用 `pi`，仅记录长度，不打印身份值或私钥。

此前把 field 4 认定为必须填写公钥，依据不充分。所核对的 iOS 26.1 静态处理链将它从历史名 `host.publicKey` 映射到 `publicCUAirPlayPairingIdentity`，对应 `pi`；真正公钥对应另一个 `pk` 属性。LIVI 也在有线/无线 StartSession 中使用 pairing ID。与此同时，DiPlay 等实现使用公钥 hex，其他实现还采用 Base64。**这说明值得核对取值差异，尚不能证明上一版公钥是当前无 TCP 的原因。** 固定版本源码与证据边界见 [LOCAL-ONLY.md](../LOCAL-ONLY.md)。

本次协议实验只改变 field 4：保持地址/监听绑定、实际端口、ACC transport type、地址组、Wi-Fi 凭据省略、Bonjour/HTTP 共享策略、重试和超时不变。CI 验证不能代替系统接口资格及真实画面验证。

## 下载与复测

下载 `CarWithin-Local-unsigned.ipa`，沿用自己的签名方式覆盖安装，核对“关于”显示 build 19。已成功载入的 MFi 身份可继续使用，无需重新准备 `certificate.p7b`、`leaf.cer`、`private.x963`。保持原 Bundle ID 与签名身份，便于保留 Keychain 中的接收器身份。

1. 先选择“仅本机（无需 VPN）”。保持与上一轮相同的网络条件，记录系统设置中 Wi-Fi 是完全关闭，还是开启但未关联；同时记录蜂窝是否可用。
2. 单次启动后留在前台，等到出现画面或自动停止。日志应显示 build 19 与 `field4=接收器配对标识 pi`。约 45 秒仍无控制连接会停止；若连接已建立但没有视频样本，总启动期限为 75 秒。
3. 停止后，手动连接默认配置的 LocalDevVPN，再单独测试一次相应模式。保存从“启动请求”到最终结果的完整日志。
4. 如果两种模式仍然都在 45 秒后无入站，下一项证据应是 iPhone 系统日志中的 CarPlay 接口/路由/发现判断。不要把继续更换 VPN 工具视为已验证的解法。

## 构建验证

发布前流程运行协议编码/校验回归测试、本机 socket 实测和完整 iOS Release 无签名构建，并核对 IPA 元数据及身份材料排除检查。具体结果见本版本提交对应的 GitHub Actions。测试验证编码和构建，不能证明 field 4 的取值已被该 iPhone 接受。

三个下载文件：`CarWithin-Local-unsigned.ipa`、`SHA256SUMS`、`build-info.json`。后者包含源码提交、实际构建号与 IPA SHA-256，真机验证状态仍标为未由 CI 执行。
